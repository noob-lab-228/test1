## Unit file
Systemd can use yours custom unit file as a process, for example - python script

Classes:

* .service
* .target
* .timer


## [Unit]
Description=Мой кастомный Python скрипт
After=network.target

## [Service]
Type=simple
ExecStart=/usr/bin/python3 -u  /home/zxc/Desktop/my_script.py
Restart=always
User=zxc

## [Install]
WantedBy=multi-user.target

# [Unut] - Общая информация и зависимости

Description=Мой первый фоновый тайм-логгер на PythonЭто человекочитаемое описание службы. Именно этот текст вы увидите на экране, когда введете команду systemctl status timelogger. Оно помогает администратору сразу понять, за что отвечает этот демон.
After=multi-user.targetЭто настройка порядка загрузки. Она приказывает: «Не запускай этот Python-скрипт до тех пор, пока система полностью не перейдет в режим multi-user (обычное рабочее состояние системы, когда готовы базовая сеть, диски и системные службы)». Это защищает скрипт от запуска в «полусырой» ОС.

# [Service] - Инструкции для запуска

Самый главный раздел. Он объясняет как, от чьего имени и в каком режиме запускать программу.Type=simpleТип запуска. simple (простой) означает, что systemd считает службу запущенной сразу же, как только выполнится команда из строки ExecStart. Процесс, запущенный этой командой, становится главным процессом службы.User=zxcБезопасность. По умолчанию systemd запускает всё от имени всемогущего суперпользователя root. Строка User=zxc принудительно занижает права службы. Скрипт будет работать с правами пользователя zxc. Если в коде Python будет ошибка (например, команда «стереть диск»), система заблокирует её, защитив ОС.ExecStart=/usr/bin/python3 /home/zxc/Desktop/time_logger.pyЭто точная команда на запуск. Важное правило systemd: здесь всегда нужно указывать абсолютные (полные) пути к файлам. Нельзя просто написать python3, нужно указать, где именно лежит бинарник интерпретатора (/usr/bin/python3) и где конкретно лежит сам скрипт (/home/zxc/Desktop/time_logger.py).Restart=alwaysИнструмент бессмертия службы. Если ваш Python-скрипт закроется сам, упадет из-за ошибки в коде или его принудительно «убьет» пользователь через команду kill, systemd мгновенно это зафиксирует и автоматически запустит его заново.RestartSec=3Таймаут перезапуска. Задает паузу перед воскрешением. Если скрипт упал, systemd не будет судорожно включать его миллион раз в секунду (чтобы не забить процессор), а подождет ровно 3 секунды и только потом сделает новую попытку запуска.

# [Install] - Правила автозапуска

WantedBy=multi-user.targetУказывает, к какому «этапу» загрузки операционной системы привязать автозапуск этой службы. Привязка к multi-user.target гарантирует, что при каждом включении вашего компьютера (виртуальной машины) этот демон будет запускаться автоматически в фоне вместе со всей остальной операционной системой.

# OOM Killer

Если заканчивается память, утилита убивает самое "жирный" процесс, рассчитывая баллы нагрузки от 0 до 1000, используя объём съеденной памяти,
возраст, корневые процессы.

## Защита.


* В юнит файле службы указать параметр -1000, -500 в таком случае процесс не будет убит

```bash
OOMScoreAdjust=-1000
```

* В директории PID указать счётчик оом, аналог первого варианта

```bash
echo -1000 | sudo tee /proc/5835/oom_score_adj
```
* Запустить службу с встроенной утилитой choom и поставить иммунитет защиты -1000

```bash
sudo choom -n -1000 python3 /home/zxc/Desktop/time_logger.py
```

# /proc

В линукс всё есть файл, физически директории /proc на диске не существует, это
своеобразное окно в оперативную память ядра Linux, там есть:

* Системная информация, например текстовый файл cpuinfo, который содержит
информацию о процессоре, version - версия ядра и дистрибутива

* Папки с цифрами ( PID процесса ): внутри папки лежит файл ( команда, 
с которой запустили программу) cmdline, файл status - сколько памяти жрёт
